Cyborg TryHackMe Walkthrough

My step-by-step notes for the Cyborg room. I cover the enumeration, web discovery, exposed Squid configuration, password cracking, Borg archive extraction, SSH access and the final Linux privilege escalation.

1. Starting with Enumeration

The first thing I normally do on a new machine is check what is actually exposed. I started with an Nmap scan against the target.

nmap -vvv 10.49.160.153

Nmap shows 22/tcp (SSH) and 80/tcp (HTTP) open.

That gave me a pretty clear starting point: SSH was available, but the web server was the obvious place to do more enumeration first.

2. Checking the Web Server

I opened the target IP in the browser and got the default Apache page. There wasn't anything useful on the page itself, so I moved on to directory enumeration.

Default Apache page.

Directory brute-forcing

gobuster dir -u http://10.49.160.153/ -w /usr/share/wordlists/dirb/common.txt

Gobuster discovers interesting directories including /admin/ and /etc/.

The two paths that stood out were /admin/ and /etc/. I checked the admin area first.

3. Looking Around /admin/

The Cyborg admin page.

The site looks like a small music-themed application. I checked the available sections instead of assuming there was an obvious exploit immediately.

The shoutbox gives useful clues about the Squid configuration and music_archive backup.

The shoutbox was the first really useful clue. It mentioned a Squid proxy configuration and a backup called music_archive. That gave me two things to investigate: the exposed configuration files and the backup.

4. Finding the Squid Hash

Since Gobuster had found /etc/, I opened it and went into /etc/squid/.

Exposed /etc/squid/ directory.

The directory contained passwd and squid.conf. The passwd file was particularly interesting because it exposed a password hash.

The exposed MD5-crypt style password hash.

5. Cracking the Hash

I saved the hash into a file called borg.hash and used John the Ripper with the RockYou wordlist.

john borg.hash --wordlist=/usr/share/wordlists/rockyou.txt

John recovers the password.

The recovered password was:

squidward

The password was a useful clue rather than an automatic SSH login. I went back to the archive mentioned on the admin page and tried it as the Borg passphrase.

6. Extracting the Borg Backup

borg extract /home/field/dev/final_archive::music_archive

When Borg asked for the passphrase, I entered:

squidward

Borg extraction and inspection of the restored files.

After extraction I checked the restored home directory. There were normal folders such as Desktop, Documents and Music. I started checking the text files because they were more likely to contain useful information.

7. Getting SSH Access

The Documents directory contained note.txt. Reading it gave me credentials for Alex:

cat note.txt
alex:S3cr3tP0s3

SSH login using the recovered credentials.

Since port 22 was open from the initial scan, I used the credentials to connect:

ssh alex@10.49.160.153

8. Getting user.txt

Once logged in, I checked the home directory and found the user flag.

ls cat user.txt

Reading user.txt.

User flag:

flag{1_hop3_y0u_k3p_th3_arch1v3s_saf3}

9. Looking for a Way to Become Root

With the user flag done, I moved on to privilege escalation. My first check was sudo:

sudo -l

sudo permission and inspection of backup.sh.

The interesting part was that Alex could run /etc/mp3backups/backup.sh as root without a password. The script was also writable by Alex. That combination is the key issue here: a root-executed script should not be modifiable by the unprivileged user who is allowed to execute it.

10. Modifying backup.sh

For this lab, I replaced the script with a Bash shell that preserves the privileged effective UID:

echo "/bin/bash -p" > /etc/mp3backups/backup.sh

I checked the contents afterwards:

cat /etc/mp3backups/backup.sh

The backup script after modification.

11. Running the Script as Root

Because sudo allowed me to execute the script as root, I ran it:

sudo /etc/mp3backups/backup.sh

Then I checked the current user:

whoami

The script gives a root shell.

12. Getting root.txt

Finally, I moved into /root and read the root flag.

cd /root ls cat root.txt

Reading root.txt from the root account.

Root flag:

flag{Than5_for_play1ng_H0pf_y0u_enJ053d}

13. What I Learned

  • Don't stop at the default web page. Directory enumeration can reveal completely different parts of an application.
  • Exposed configuration files can contain hashes, usernames and useful paths.
  • A password recovered from one part of a lab can become useful when another clue points to the same backup or service.
  • When I extract a backup, I should inspect restored text files for credentials and other useful information.
  • After getting a normal user shell, sudo -l is one of the first privilege-escalation checks I should make.
  • A root-run script that is writable by the current user can lead to arbitrary command execution as root.
